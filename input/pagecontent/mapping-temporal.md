### Temporal data

openEHR's temporal values inherit from the abstract `DV_TEMPORAL` class:
`DV_DATE`, `DV_TIME`, `DV_DATE_TIME`, and `DV_DURATION`. FHIR uses the `date`,
`dateTime`, `instant`, and `time` primitives, plus `Duration` (a constrained
`Quantity`) and `Period`.

Both systems use ISO 8601, which makes this category look easier than it is.
Six facts govern the rows.

**The two ISO 8601 subsets are not the same subset.** openEHR permits compact
forms — `20250301`, `T143000` — while FHIR requires the extended form —
`2025-03-01`, `14:30:00`. Compact values SHALL be expanded before mapping to
FHIR. The precise comparison is published as a machine-generated table on
[Cross-Cutting Concerns](cross-cutting.html), rendered directly from the code
that implements the conversion, so the guide and the reference implementation
cannot disagree about it.

**Partial precision is meaningful and SHALL be preserved.** Where an openEHR
value is partial — year and month only — the FHIR lexical form is **truncated**
to match, never padded. `202604` becomes `2026-04`, not `2026-04-01`. Padding
invents a day that the source did not record.

That rule holds for every partial form the FHIR regexes admit, which is every
`date` and every `dateTime` down to the year. It **cannot** hold in one place:
FHIR `time` makes seconds mandatory, and FHIR `dateTime` makes them mandatory
once a time is present, so an openEHR `14:30` or `2026-03-01T14:30` has no
shorter FHIR form to truncate to. Those two values SHALL be completed to
`14:30:00` and `2026-03-01T14:30:00`, and the completion is a **named loss** —
`DV_TIME.value[minute-precision]` and `DV_DATE_TIME.value[minute-precision]` —
not a silent one. FHIR additionally requires a UTC offset alongside a time in a
`dateTime`: that offset SHALL come from the source or its context, and a
data-type conversion never invents one. A `DV_DATE_TIME` that states a time and
no offset is therefore **refused** — nothing is produced, rather than a value
padded with `Z` that would state a time zone the source did not. That gap is
the `DV_DATE_TIME.value[no-offset]` row below. It is a **narrative** rule rather
than a lexical one: R5's published `dateTime` regex makes the zone group
optional, and only the sentence beside it requires the offset.

**Fractional seconds differ in width.** FHIR allows up to nine decimal digits;
openEHR restricts to three. Excess precision is truncated when mapping FHIR →
openEHR, which is a named drop rather than a rounding decision.

**FHIR `time` cannot carry a time zone, and no extension rescues it.**
`dateTime` and `instant` carry an offset directly; `time` does not. The
`timezone` extension does admit `time` as a context, but it declares
`value[x]: code 1..1` with a **required** binding to
`http://hl7.org/fhir/ValueSet/timezones`, whose codes are IANA zone names.
`+01:00` is not a permissible code, and a zone name is not an offset — one zone
name denotes different offsets across daylight saving. A `DV_TIME` offset is
therefore a **named drop**, published at `DV_TIME.value[timezone]`, and where
the offset is clinically significant the value SHOULD be mapped to a `dateTime`
instead. The question of how else to carry it is
[open](open-items.html).

**Some FHIR resources split a date and its time across two elements.**
`Patient.birthDate` is a `date`, with the time conveyed by the
`patient-birthTime` extension. A mapping engine has to know these
element-specific patterns; they are not derivable from the data type alone.

**Duration needs a real conversion.** ISO 8601 durations and UCUM quantities are
different representations, and not every ISO 8601 duration has a UCUM
equivalent. The conversion is implemented in the
[reference implementation](reference-implementation.html) and the
non-convertible cases are reported rather than silently approximated. Two
properties of that conversion are easy to miss. **Durations may be negative**,
and the sign belongs before the `P`: openEHR's `Iso8601_duration` gives `-P3M`
as its own example while requiring every individual component to be
non-negative, so `-P3M` is legal and `P-3M` is not. And **a millisecond-coded
`Duration` does not come back as one**: openEHR has no millisecond designator,
so `5 ms` can only be written `PT0.005S`, which reads back as `0.005` seconds —
a different stated number in a different unit. That is published as its own
`Duration.value[ms]` gap rather than folded into the value row's verdict.

Date and time intervals map to `Period` and are covered here. Numeric intervals
map to `Range` and are covered in [Quantities](mapping-quantity.html).

See [Conventions](conventions.html) for how to read the tables.
