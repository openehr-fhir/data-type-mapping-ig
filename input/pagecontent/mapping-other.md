### Other data

This category holds the types that do not fit any of the others: encapsulated
binary and parsable content, and state machines.

**`DV_MULTIMEDIA` ↔ `Attachment`** is the substantial mapping here. The two
types agree on the essentials — media type, data, size, an integrity hash, a URI
alternative to inline data, and a language — and diverge on almost everything
around them. `DV_MULTIMEDIA` carries a compression algorithm, an integrity check
algorithm that need not be SHA-1, and a thumbnail; `Attachment` carries a
creation timestamp, height, width, frames, duration, and pages. Neither set has
a home on the other side, and **each is recorded as its own `unmapped` row**
naming who owns it. Two qualifications matter. The `Attachment` elements are
owned by `openehr-modelling` — the openEHR modelling team, which is a **team,
not a ticket**; there is no Jira number to quote, and the proposal to fold them
into the published *Media File* CLUSTER archetype is tracked on
[Open Items](open-items.html). And `Attachment.language` is **not** among them:
`DV_MULTIMEDIA` inherits `language` from `DV_ENCAPSULATED`, so that one maps,
losing only the `CODE_PHRASE`'s terminology identifier. **No extension, code
system, or value set is invented here for any of the rest.**

**`DV_PARSABLE`** wraps a string with a `formalism` naming the syntax it is
written in. The value maps to a FHIR `string`, or to `markdown` where the
formalism is markdown. **The `formalism` itself has no FHIR home.** The
`mimeType` extension is not it: its declared context is `Questionnaire.item`
and `ElementDefinition`, not `string` or any data type, and its purpose is a
design-time constraint on the attachments an element permits rather than a
statement about an instance. No substitute is invented here, so the gap is
published and the mapping is **one-directional**: a `DV_PARSABLE` becomes a
`string`, and a `string` alone cannot become a `DV_PARSABLE`, because
`formalism` is mandatory and only the element definition knows it. The decision
is [open](open-items.html).

**`DV_STATE`** carries a coded value plus an `is_terminal` flag and belongs to
an instruction state machine. FHIR has no data type for it: FHIR models workflow
state as resource-level elements such as `Task.status`, with its own state
machine. The value can be carried as a `CodeableConcept`, but the state machine
it belongs to cannot, so this is largely `unmapped` and the reason is recorded
rather than papered over.

`DV_ENCAPSULATED`, the abstract parent of `DV_MULTIMEDIA` and `DV_PARSABLE`, is
also noted here. The openEHR Reference Model is the authority for its
definition, and this guide cites the RM rather than any downstream
representation of it.

Reviewer coverage in this category is uneven — several of these types were never
reviewed from the FHIR side. That is published in full on
[Open Items](open-items.html) rather than smoothed over, and rows the
specifications do not clearly support are recorded `open` rather than asserted.

See [Conventions](conventions.html) for how to read the tables.
