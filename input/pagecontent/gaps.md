### Gaps

A gap is a place where one standard carries information the other has nowhere to
put. Gaps are **not** failures of this guide; they are facts about two
independently developed specifications, and the guide's job is to state them
precisely rather than to bridge them by invention.

Gaps run in **both directions**, and the two directions are genuinely different.
An openEHR attribute with no FHIR home is a different problem from a FHIR
element with no openEHR home, and they are owned by different groups.

This page publishes four inventories.

- **openEHR → FHIR** — openEHR attributes and types that cannot be carried into
  FHIR, at both the data-type and the archetype/resource level.
- **FHIR → openEHR** — FHIR elements that cannot be carried into openEHR.
- **FHIR features with no openEHR counterpart** — FHIR features for which the
  openEHR Reference Model has no equivalent at all. A *feature* here is a whole
  data type, a single element, or a named sub-case of one: eleven of the entries
  are whole types and the rest are elements or sub-cases. These are recorded
  with the reason and are not investigated further.
- **Not yet discussed** — types on either side that the working group has not
  examined. These carry no fidelity claim, because nobody has checked.

Every row on this page is an ordinary ledger row and carries the same two
mandatory citations as any mapping row. A row for a type with no counterpart
cites the **inventory page** of the standard that lacks it — the openEHR RM
*Data Types Information Model*, or the FHIR R5 *Data Types* page — so that "no
counterpart exists" remains a sourced claim rather than an assertion.

Where a gap has an owner, the owner is named: an HL7 Jira ticket, the openEHR
modelling team, or the joint working group. [Open Items](open-items.html) tracks
their status.

**Nothing on this page is closed by inventing a FHIR construct.** No extension,
code system, or value set is defined by this guide to fill a gap. Where the
right answer is an archetype, the guide links the archetype and says who owns
it. Where the right answer is a change to one of the two standards, the guide
names the ticket.

**Each directional inventory contains what its heading says, and only that.**
*openEHR → FHIR* lists openEHR features FHIR cannot receive, so every row has a
real openEHR attribute; *FHIR → openEHR* lists FHIR features openEHR cannot
receive, so every row has a real FHIR element. The FHIR types with **no openEHR
counterpart at all** are a third thing and have their own inventory below; they
are not repeated in the FHIR → openEHR table.

**`Money` is not among them.** openEHR has no *dedicated* monetary type, which
is a real observation, but a FHIR `Money` is reached from a `DV_QUANTITY`
carrying an ISO 4217 currency code in `units` — a published, fixture-backed
mapping, set out on [Quantities](mapping-quantity.html). Listing `Money` as
having no openEHR counterpart would have the guide answering the same question
two ways on two pages, so it is not listed; an openEHR Reference Model proposal
for a first-class `Money` type is open and is tracked on
[Open Items](open-items.html).

See [Conventions](conventions.html) for how to read the tables.

### FHIR features with no openEHR counterpart

FHIR features for which the openEHR Reference Model has no equivalent at all. A
**feature** is a whole data type, a single element, or a named sub-case of one —
`Address` and `HumanName` are whole types, `Identifier.use` and
`Duration.code` are elements, and `Quantity.comparator[ad]` and
`Attachment.size[overflow]` are named sub-cases. Each cites the openEHR Data
Types inventory page, so "no counterpart exists" remains a sourced claim.
